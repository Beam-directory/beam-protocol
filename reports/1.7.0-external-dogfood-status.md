# Beam 1.7.0 External Dogfood Status

Status: `blocked`

Last updated: `2026-06-09`

## Summary

The repo-owned hosted-adoption work for Beam `1.7.0` is complete enough to stage a candidate, but the release is still blocked on one explicitly external gate:

- real external dogfood and adoption evidence

This is tracked as GitHub issue `#196`.

## What is already proven internally

- packaged host installer and bootstrap-token flow
- guided enrollment links and operator onboarding in the fleet UI
- operator/member management with explicit RBAC administration
- screenshot baselines and visual regression gates in CI
- fleet analytics and support-bundle export
- buyer dry run
- installer dry run
- operator dry run
- repo-owned UI smoke and visual compare

The repo now also includes a dedicated packet generator for the external pass:

- `npm run workspace:external-dogfood-pack -- --tester-name "Jane Example" --tester-email "jane@example.com" --host-label "Jane MacBook"`
- release-evidence form: `BEAM_ADMIN_TOKEN=<admin-session-token> npm run workspace:external-dogfood-pack -- --directory-url https://api.beam.directory --workspace openclaw-external-dogfood --tester-name "Jane Example" --tester-email "jane@example.com" --host-label "Jane MacBook" --require-public-directory`

That command writes one host-install packet, one feedback template, and one structured `.completion.json` template under `tmp/external-dogfood-pack/`.
The `--require-public-directory` guard is intentionally strict: localhost rehearsal packs are useful, but they do not count toward `#196` release evidence.
After each real external run, the `.completion.json` file is the handoff point for the release evidence JSON.
When all completion files are filled, `npm run production:external-dogfood-assemble -- --input-dir tmp/external-dogfood-pack --output reports/1.7.0-external-dogfood-evidence.json` assembles the release evidence file only if the completed packets satisfy the production gate.

The packet generator was re-verified locally on `2026-06-09` against the quickstart control plane:

- `npm run workspace:external-dogfood-pack -- --tester-name "Production Readiness Probe" --tester-email "probe@example.invalid" --host-label "2026-06-09 readiness probe" --operator-name "Beam Operator" --operator-email "ops@beam.local"`: `PASS`
- output directory: `tmp/external-dogfood-pack/`
- note: generated packet dates use the shared UTC `formatDate()` helper, so a late-night CEST run can emit the previous UTC date in file names.

The repo now also includes a machine-checkable evidence gate:

- template: `reports/1.7.0-external-dogfood-evidence.template.json` (`template: true`, intentionally rejected by the production gate)
- command: `npm run production:external-dogfood`
- assembler: `npm run production:external-dogfood-assemble`
- current expected result: `FAIL` until `reports/1.7.0-external-dogfood-evidence.json` exists and proves the required external adoption evidence

## What is still missing

The missing evidence is not another local harness run. The missing evidence is a real external adoption pass that shows at least:

- at least two operators participating outside the local maintainer loop
- at least five non-local hosts installed through the packaged bootstrap flow
- at least one fresh-machine onboarding with no preloaded repo state
- at least one support bundle or fleet analytics handoff used in a realistic support/debug situation
- written feedback proving the hosted-adoption path works for someone other than the local repo maintainer

The evidence file must satisfy the production checker thresholds:

- `operators`: at least two distinct entries with `external: true`
- `hosts`: at least five entries with `external: true`, `installed: true`, and `bootstrapFlow: "packaged"`
- at least one host with `freshMachine: true` and `noPreloadedRepoState: true`
- at least one `supportHandoffs` entry of type `support-bundle` or `fleet-analytics` with `usedInRealDebug: true`
- at least two written feedback entries with `external: true`

## Release implication

Beam `1.7.0` is currently:

- `candidate-ready` for the internal, repo-owned scope
- `no-go` for the public release cut

The `1.7.0` release should not be tagged until `#196` is closed with real external evidence.
